AI in the SDLC

Six phases, two loops: how I'm putting AI agents across the entire SDLC

Everyone uses AI to write code faster. Cool. Then the code piles up waiting for review. So I mapped the whole lifecycle and put an agent on every phase.

Said Reklaoui · 5 October 2026 · 5 min read

Here's what bugs me about how most teams “adopt AI”: they plug it into one place, writing code, and call it done. The code gets written faster, and then it just sits there. Waiting for review. Waiting for someone to check it actually works. Waiting in the on-call queue when it breaks.

You didn't speed anything up. You moved the bottleneck.

So I stopped collecting AI initiatives and did something more boring. I took the whole lifecycle, six phases, and asked two questions for each one: where does this phase live, and what would an agent do there? This is the map that came out of it, and it's what I'm building against as an AI engineer at Oneclick.

Fair warning: this isn't a victory lap. The platform is up, and most of what sits on it is being built right now. I'm writing it down because drawing this map is what made the plan click.

It all runs on one platform

I didn't want six tools duct-taped together. So I built one internal platform where every agent is defined by its job: which model, what instructions, what workspace, what it's allowed to touch. Agents react to events (a new ticket, a message, an alert) and share the same skills and the same company knowledge.

Two decisions I'd make again tomorrow:

  • Never marry a model. Any agent can swap its model without a rewrite. Today's best model won't be next quarter's.
  • Agents get their own account. I want to see exactly what they cost, separate from what people cost.

Phase by phase

1. Plan

The biggest win here isn't a tool, it's a habit. Engineers hand the agent tiny tasks and then babysit every line. That's buying a car and pushing it. A ticket should describe the problem and what done looks like, the way a product person would write it, and then you let the agent run. Where I want us: several projects moving in parallel, with agents carrying them for days.

2. Build

Skills and commands are a product, not a folder of prompts. I'm auditing ours so each one is tuned to the model that runs it, with evals that prove a change actually made it better. The first big bet is an agent-driven backend migration: one feature, end to end, before anyone tries to scale it.

3. Review

Once agents write the code, review is where everything jams. One engineer with agents opens more pull requests a day than anyone can read. So I put a gate in front of it: every PR gets classified by risk. Low: an agent reviews it. Medium: a paired review. High: full human review. Human attention goes where it actually changes the outcome.

4. Verify

“It compiles” is not proof. I give the agent the same things a developer uses to check their own work: a browser, the dev database and its own test users in the app. Then it attaches the evidence to the ticket. The reviewer starts from proof, not from trust.

5. Operate

Two agents on the production side. One reads incidents, sets the priority and writes a first root-cause analysis before a human even opens it. The other reads the errors and opens a pull request with the fix, auto-merged when the risk is low.

6. Learn

This one's my favourite. An agent reads every review comment, spots the feedback that keeps coming back and rewrites the skills and instructions the other agents work from. Say it once and you never have to say it again.

The loops are the whole point

A straight line from Plan to Operate is just automation. The two dashed arrows are what make it get better:

  • Incident response back to Review. An agent's fix is still a pull request. It goes through the same gate as everything else, and only low-risk fixes skip the human.
  • Outer loop back to Build. Review feedback flows into the skills the next build uses. Every review makes the next PR a little better.
Without the loops, each phase gets faster. With them, the system gets better every time it runs.

The boring part that decides everything

  • One source of truth, for people and agents. Agents can't act across the stack without business context. Where that knowledge lives, and how docs for humans and context for agents split, is the decision I'm still closing.
  • Delegate problems, not tasks. It's a habit, and it's the hardest one to change.
  • Go deep before going wide. One project end to end, then pull out the patterns. Rolling half-baked agents out to every team at once teaches you nothing.
  • Write the playbook. How we verify, which commands, how we work. A new joiner should be useful from day one.

What's next
